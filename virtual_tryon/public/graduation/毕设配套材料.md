# 交互式虚拟试衣系统毕设配套材料

题目：基于深度学习的交互式虚拟试衣系统设计与实现

适用范围：本科毕业设计的选题说明、开题、系统演示、技术交接与答辩准备。以下安排围绕当前已有实现编写，学校签章、教师意见、个人信息与日期由本人和指导教师填写。

## 一 项目简介

本课题针对线上服装选购中的试穿需求，设计并实现一套基于深度学习的摄像头虚拟试衣系统。系统采用前后端分离架构，用户可通过浏览器采集人物画面，选择内置样衣或上传服装图片，查看换衣效果。后端以FLUX.2 Klein生成模型为核心，结合FluxRT推理框架，在远程GPU上完成服装参考图引导的完整图像生成，并通过WebSocket将结果返回前端。针对连续处理中的延迟与卡顿，系统采用后台异步编码、最新帧调度、传输背压控制和服装参考特征复用，并提供可选补帧显示。系统建立了覆盖采集、生成、传输和绘制的分阶段计时机制，围绕半身构图、人物移动及转身开展测试，分析响应延迟、画面连续性与服装外观一致性，为交互式虚拟试衣的工程设计与优化提供实践依据。

## 三 开题报告

### 3.1 选题背景

在线服装展示主要依赖商品图与模特图，用户难以判断服装与自身外观的组合效果。虚拟试衣通过图像合成提供直观参考，而摄像头交互进一步要求效果随人物运动变化。现有生成方法能够改善单帧自然度，但在浏览器、远程网络和GPU串联的环境下，单帧效果并不自动转化为流畅体验。

因此，本选题把可用系统与可解释测试作为共同目标，在实现服装条件生成的同时，研究异步编码、最新帧调度、背压和显示缓冲对交互的影响。研究对象是视觉试穿原型，不是服装尺寸测量、物理布料模拟或电商交易系统。

### 3.2 国内外研究与技术路线

虚拟试衣包含服装形变与融合、扩散式图像生成、视频连续生成等方向。CP-VTON和VITON-HD提供对齐与融合研究基础，CatVTON简化扩散式试衣结构。通用图像编辑模型可以接受参考服装，但仍需要检验身份保持和细节一致性。固定样衣方法可以利用逐衣训练提高局部效率，却限制任意新图即时试穿。

本项目以完整画面图像编辑为主路线，以旧版衣层Warp和固定样衣RTV为对照。浏览器通过Worker编码，使用WebSocket向远程服务传输人物帧，后端以Klein与FluxRT生成并返回结果。将分阶段计时贯穿全链路，避免只报告生成器吞吐或插值显示数量。

### 3.3 关键问题与方法

问题一是输入不完整与半身构图。主路径直接生成整幅输入，避免把是否检测到髋部等关键点作为生成前置条件。问题二是处理速度低于相机帧率，采用有界上传与替换等待帧控制积压。问题三是视觉连续与背面错误，需要通过图案服装与动作脚本分析，不能仅用提示词或补帧解决。问题四是远程资源不可用时的演示，采用明确标注的本地功能降级。

### 3.4 可行性与风险

已有前端与后端原型能够完成服装上传和全帧输出，历史运行日志可用于性能分析，隔离固定样衣实验提供另一种证据。技术风险主要是原生生成帧率不足、远程传输长尾、快速运动与正背面不一致。资源风险是GPU供应中断，应保留免GPU模式与历史证据。

应对措施是使用可重复测试和明确的阶段指标，而不是继续堆叠同类参数微调。若三次同类调整不能改变体验，需要重新评估逐帧架构与时序建模假设。论文完成不以宣称商业级实时效果为前提，结论应与真实证据一致。

### 3.5 可说明的特色

特色包括服装图片通用输入与完整生成流程结合、浏览器采集编码移至后台线程、有界最新帧调度、可追溯的逐帧日志，以及对离线演示和真实模型输出的明确区分。这些属于系统设计和工程改进，不能写成自行提出新的基础生成模型或实现全新服装物理算法。

## 四 需求与设计说明书

### 4.1 功能边界

系统包含主页、试衣工作台、内置衣柜、自定义上传、相机、生成控制、数字诊断、保存结果和材料下载。系统不包含账号注册、购物支付、云端个人衣柜和多租户GPU队列。缺少这些功能不影响本课题对交互式试衣流程的研究与验证。

### 4.2 技术栈

| 层次 | 技术 | 用途 |
| --- | --- | --- |
| 前端 | 原生JavaScript、HTML、CSS、Vite | 页面、构建与按需加载 |
| 采集显示 | getUserMedia、VideoFrame、Canvas | 摄像头与图像展示 |
| 异步处理 | Web Worker、OffscreenCanvas | 后台编码与主线程隔离 |
| 通信 | 二进制WebSocket、SSH隧道 | 会话传输与受限连接入口 |
| 服务推理 | FastAPI、Uvicorn、PyTorch、CUDA | GPU任务与接口 |
| 模型 | FLUX.2 Klein 4B、FluxRT、可选RIFE | 完整图像编辑和插值 |
| 回归 | Playwright | 协议、交互与资源管理 |

MediaPipe、CatVTON与WebGL服装网格是旧版对照；RTV、BEV、DensePose与EGL属于隔离实验。默认路径没有使用React、Three.js或完整布料物理系统，不应在答辩中误报。

### 4.3 页面状态与接口

主页地址为本地8766根路径，工作台为/studio，免GPU演示为/studio?demo=1。完整生成状态接口为本机8022的/api/status，生成会话为/api/stream，耗时同步为/api/telemetry。8022通过SSH转发至远端回环8030。旧版8020和8021不属于默认完整生成链路。

接口成功、工作空间运行、模型ready和一次真实生成是四个不同检查层级。看到8022监听不能跳过远端进程检查，看到ready也不能以零输入HTTP请求替代一次真实协议验证。

### 4.4 数据处理

用户图片限JPG、PNG、WebP，最大8 MB。上传后归一化为最长边不超过1024像素的JPEG，在当前页面维护对象URL。人物采集使用512×512等比留边；生成输出按320、384或512档位处理。相机不采集音频，关闭时停止视频轨道。

## 五 部署与操作手册

### 5.1 无GPU启动

进入virtual_tryon目录，先运行npm ci安装锁定依赖；已有依赖时无需重复安装。随后执行以下命令，仅启动前端，不启动本机CatVTON，也不连接远程GPU。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-demo.ps1 -Demo
```

访问http://127.0.0.1:8766/查看主页，选择“免GPU交互演示”进入工作台。选择衣服、上传图片并打开摄像头，检查本地预览即可。该模式没有模型生成结果，也不会因为操作按钮自动申请GPU资源。

### 5.2 远程生成启动

确认原RTX 5090工作空间已有资源并处于运行状态，且原FluxRT环境和权重仍存在。在virtual_tryon目录执行以下命令，连接原隧道并检查服务。脚本不负责创建或启动工作空间。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-demo.ps1 -Remote
```

打开/studio，点击重新检查服务，待AI服务就绪后启动摄像头。选择流畅或均衡档，开始连续生成。参考衣服上传与人物帧会发送至已配置的远程服务，不传送给付费第三方视频API。

### 5.3 使用顺序

1. 在右侧选择内置样衣，或上传清晰且完整的衣服参考图。
2. 打开摄像头并允许浏览器访问，保持光线均匀且上半身可见。
3. 服务就绪后开始生成，选择低延迟直接显示或平滑补帧。
4. 查看采样到绘制与模型耗时，必要时导出数字日志或主动保存AI画面。
5. 演示结束后停止生成并关闭摄像头。

### 5.4 常见问题

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 服务离线 | 无GPU资源、隧道断开、远端进程未运行 | 先用演示模式，恢复资源后逐层检查 |
| 摄像头拒绝 | 浏览器权限或设备占用 | 授权本地页面，关闭占用设备的其他软件 |
| 有隧道仍报错 | 远端8030未启动或模型未ready | 检查后端，不以8022监听判断成功 |
| 动作跟随慢 | 原始生成、链路或显示缓冲 | 导出逐帧日志，不将补帧当推理加速 |
| 背面出现胸图 | 单图条件缺乏背面约束 | 记录失败案例，当前尚未可靠解决 |
| 刷新后上传消失 | 参考图为页面临时对象 | 重新上传；不声称已实现云端衣柜 |

## 六 测试方案与实验记录规范

### 6.1 基础用例

主页应独立于GPU与相机引擎；演示模式应允许上传与相机并且没有推理请求；GPU503时保持本地预览；更换衣服取消旧会话；停止清除Worker、定时器与旧画面；390像素宽度没有整页横向滚动。默认完整路径不能调用旧版衣层裁切。

### 6.4 结果解释

采样到绘制是浏览器同一单调时钟的总耗时；模型耗时是GPU侧阶段；RTT是特定探测消息的往返；固定RTV流水线吞吐不包含网络与显示。中位数不能跨阶段直接相加。静态缓存75.9 ms和首帧冷启动2.47秒属于不同输入条件，不应挑出较小值作为真人连续性能。

当前历史P50为490.6 ms并不意味着每帧如此；P95为844.6 ms也不证明长时间运行稳定。真实体验仍需动作与视觉证据，用户反馈与数字记录共同用于判断。

## 七 答辩讲稿与演示安排

### 7.1 五分钟讲稿

各位老师好，我的毕业设计题目是《基于深度学习的交互式虚拟试衣系统设计与实现》。课题面向线上服装选择，目标是让使用者通过摄像头和服装图片查看换衣效果，并对连续处理中的响应延迟进行分析。

系统采用浏览器与远程GPU协作的架构。前端使用原生JavaScript、Vite和Canvas，支持内置样衣、任意服装图片上传和半身摄像头输入。后端使用FastAPI、PyTorch和CUDA，集成FLUX.2 Klein与FluxRT，生成整幅换衣画面，而不是只把服装图片投影到身体关键点。

本项目的主要工程工作包括后台异步编码、有界上传窗口、最新等待帧替换、缓存复用和分阶段数字日志。相机编码在Worker内进行，避免阻塞页面；当输入速度高于生成速度时保留最新等待帧，避免积累旧动作；显示时区分模型原帧和插值帧，便于解释实际速度。

接下来演示主页、衣柜与上传功能，再展示相机预览、服务状态和诊断入口。若现场GPU资源不足，使用明确标注的免GPU模式展示操作，并使用已有历史实验说明真实生成情况，不把合成演示当作模型输出。

历史真人流畅档30个原帧的端到端延迟中位数为490.6毫秒，95分位844.6毫秒，实际原帧显示约4.77帧每秒。结果说明系统功能链路已经建立，但逐帧生成和远程传输仍限制流畅度。固定样衣RTV对照虽然能获得不同的速度与背面表现，却依赖逐衣训练，因此没有替代必须保留的任意图片上传。

本课题完成了交互原型与可追溯测试机制。当前不足主要是快速动作下的连续性、胸前图案复制到背面，以及原生生成速度。后续将研究支持服装条件的时序模型，并进一步拆分传输瓶颈。以上是我的汇报，谢谢各位老师。

## 八 答辩问题准备

### 8.1 为什么用完整生成而不是关键点贴图

贴图能够低成本地跟随粗略位置，但难以重新生成衣服褶皱和真实遮挡。完整生成尝试同时处理人物与服装关系，更符合视觉穿着目标，代价是推理更重并存在时序不稳定。项目保留旧版作为对照，没有用贴图隐藏生成速度问题。

### 8.2 你的独立工作是什么

独立工作包括需求与页面设计、生成服务接入、浏览器编码与调度、会话取消和资源释放、故障定位、逐帧数字诊断及实验分析。基础模型和第三方框架来自公开项目，不能说成自行训练或提出。

### 8.3 为什么不是只换成更快GPU

历史记录显示模型阶段仅占总延迟的一部分，剩余项还包含传输、缓冲与调度。更快GPU可能缩短推理，但不能自动消除链路延迟，也不能修复服装背面语义错误。因此需要受控链路实验和时序建模。

### 8.4 补帧能否解决实时性

补帧可能减轻视觉跳变，但需要相邻帧并增加等待，不能提高原始生成速度。系统显示原生与插值两种帧率，并把播放缓冲计入采样到绘制。

### 8.5 固定样衣实验为什么不直接上线

固定样衣权重依赖该件衣服的训练素材，不能直接接受任意新服装图片；整体流水线还需要人体估计等阶段。项目的上传能力不能被固定衣柜替代，因此把它作为隔离对照。

### 8.6 背面为何容易错误

单张正面参考没有完整背面信息，逐帧编辑又缺乏稳定的朝向与服装记忆，可能把胸前图案错误复制。当前通过图案样衣转身测试记录该失败，尚无可靠修复，不应宣称完全恢复未观测结构。

### 8.7 如何证明优化有效

对浏览器优化使用重复帧绘制计数、后台停止与回归测试；对体验优化需要同人物同动作同网络的前后对照，比较原始FPS、P50、P95与视觉错误。不同会话或缓存静态图的单次速度不足以证明改善。
